# Паспорт проекта

## Общие сведения

**Название команды:** Стрик в дуолинго 
**Название продукта:** AccessFlow
**Коды участников:** `M1`, `M2`, `M3`
**Статус ранней калибровки:** `черновик`

## 1. Назначение

AccessFlow является сервисом для подачи согласования и контроля временных допусков студентов и сотрудников в различных помещения кампуса. Продукт избавляет подразделения от бумажных служебных записок и несогласованных визитов, обеспечивая прозрачный цифровой маршрут согласования для заявителей, заведующих помещениями и сотрудников бюро пропусков. Собственная предметная логика включает валидацию временных окон и лимитов одновременного нахождения людей, автоматический ролевой переход по графу состояний заявки и фиксацию неизменяемого аудиторского следа каждого решения

## 2. Граница продукта

**В продукт входит:**

- Серверное Web API для управления полным жизненным циклом заявок на допуск
- Разграничение прав доступа на основе ролей и зон ответственности за конкретные помещения
- Бизнес-логика контроля ограничений: проверка пересечений временных интервалов, вместимости помещений и графика доступности
- Ведение журнала посещений
- Реляционное хранилище данных учетных записей, помещений, заявок и истории действий

**Внешнее окружение и внешние системы:**

- Клиентские приложения: веб-клиент или интеграционные HTTP-клиенты 
- Внешняя система контроля и управления доступом кампуса: в рамках проекта моделируется через сервисный интерфейс подтверждения прохода
- Почтовый шлюз для уведомлений.

**Команда сознательно не реализует:**

- Мобильные приложения под iOS/Android.
- Интеграцию с физическими аппаратными контроллерами турникетов и считывателями карт.
- Биометрическое распознавание лиц или отпечатков пальцев.
- Модули платного бронирования, эквайринг и биллинг.
- Сложные аналитические дашборды с прогнозной загрузкой помещений.

## 3. Пользователи и доступные действия

| Пользователь или роль | Кто это | Что может делать | Что ему недоступно |
| --- | --- | --- | --- |
| **Неавторизованный пользователь (Гость)** | Любой посетитель без аутентификации | Просматривать публичный перечень помещений, их назначение и общие правила подачи заявок | Подавать заявки, просматривать чужие заявки, согласовывать допуски, изменять данные |
| **Заявитель (Студент / Сотрудник)** | Аутентифицированный пользователь кампуса | Создавать, редактировать (до отправки) и отзывать свои заявки; просматривать историю и статусы своих заявок | Согласовывать заявки (включая свои собственные), просматривать заявки других пользователей, изменять правила помещений |
| **Куратор помещения (Зав. лабораторией)** | Ответственное лицо за конкретную учебную или исследовательскую зону | Просматривать поданные заявки в закреплённые за ним помещения; согласовывать (Approve) или отклонять (Reject) их с обязательным комментарием; задавать лимиты вместимости своего помещения | Согласовывать заявки в чужие помещения; выдавать финальный пропуск в обход регламента; удалять историю согласований |
| **Оператор бюро пропусков (Администратор СКУД)** | Сотрудник службы безопасности / бюро пропусков | Просматривать согласованные кураторами заявки; активировать временный пропуск (переводить в статус «Действителен»); досрочно аннулировать допуск при нарушении регламента; просматривать сквозной журнал аудита | Согласовывать заявку за куратора помещения; модифицировать содержание исходной цели визита заявителя; удалять записи журнала аудита |

## 4. Сквозные сценарии

### Сценарий 1. Подача заявки на проведение эксперимента в лаборатории
- **Участники:** Заявитель (Студент/Сотрудник).
- **Начальное условие:** Заявитель аутентифицирован в системе; выбранная лаборатория активна в каталоге.
- **Основные действия:**
  1. Заявитель выбирает помещение, указывает желаемый временной интервал, цель доступа и список соавторов/оборудования
  2. Сервер проверяет корректность интервала 
  3. Заявитель подтверждает отправку заявки.
- **Результат:** Заявка сохранена в системе и поставлена в очередь на рассмотрение куратору лаборатории; заявитель видит её в личном кабинете со статусом `Pending`.
- **Какие данные или состояние изменяются:** В БД создается запись `AccessRequest` в статусе `PendingApproval`; уменьшается доступный лимит слотов на указанный интервал времени; в журнал аудита вносится запись о создании заявки.

### Сценарий 2. Рассмотрение заявки ответственным лицом
- **Участники:** Куратор помещения, Заявитель (получатель результата).
- **Начальное условие:** Заявка находится в статусе `PendingApproval`; пользователь является назначенным куратором данного помещения.
- **Основные действия:**
  1. Куратор открывает список заявок, ожидающих решения, и изучает обоснование
  2. Куратор принимает положительное решение или отклоняет заявку с указанием причины
  3. Сервер проверяет, что согласующий действительно привязан к данному помещению и не является автором заявки
- **Результат:** Заявка переходит в статус `Approved` (одобрена для бюро пропусков) либо `Rejected` (отклонена, процесс завершен).
- **Какие данные или состояние изменяются:** В объекте `AccessRequest` изменяется поле `Status` на `Approved` или `Rejected`, заполняются поля `ReviewedBy`, `ReviewedAt`, `ReviewNotes`; в журнал аудита записывается событие принятия решения.

### Сценарий 3. Валидация допуска и фиксация входа
- **Участники:** Оператор бюро пропусков, Заявитель.
- **Начальное условие:** Заявка находится в статусе `Approved`; текущее время попадает в разрешённый временной интервал заявки.
- **Основные действия:**
  1. Заявитель предъявляет идентификатор
  2. Оператор или модуль интеграции отправляет запрос на верификацию и активацию допуска.
  3. Сервер проверяет статус заявки, текущее время и отсутствие факта аннулирования.
  4. Сервер подтверждает валидность допуска и переводит заявку в статус `Active`
- **Результат:** Заявитель получает физический доступ; система отмечает факт использования допуска.
- **Какие данные или состояние изменяются:** Статус заявки обновляется на `Active`; создается запись в журнале регистрации проходов `AccessLog`.

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| **Заявка на доступ (`AccessRequest`)** | Заявитель, Куратор, Оператор бюро пропусков | Низкие/средние  | **Критичные:** Несанкционированное изменение статуса приводит к незаконному проникновению в спецпомещения; удаление или недоступность срывает проведение запланированных занятий/экспериментов |
| **Правила и квоты помещения (`RoomPolicy`)** | Кураторы помещений, Администрация кампуса, Служба безопасности | Низкие (правила внутреннего распорядка, лимиты мест, часы работы) | **Высокие:** Завышение лимита вместимости приводит к нарушению норм пожарной безопасности и порче оборудования; сброс времени работы блокирует возможность подачи заявок |
| **Журнал аудита решений (`AuditLogEntry`)** | Служба безопасности, Руководство университета | Средние (раскрытие служебных комментариев, причин отказов, идентификаторов сотрудников) | **Критичные:** Неправильное изменение или удаление записей скрывает факты злоупотреблений, делает невозможным служебное расследование инцидентов физической безопасности |

## 6. Компоненты и внешние взаимодействия

Продукт состоит из следующих логических компонентов:
1. **API Server (ASP.NET Core):** Монолитное веб-приложение, реализующее REST API, аутентификацию или авторизацию, валидацию входных данных, доменную логику переходов состояний и запись аудита.
2. **База данных (PostgreSQL / SQLite):** Хранит реляционные таблицы пользователей, помещений, заявок, правил и неизменяемых аудиторских логов.
3. **Фоновый процессор (IHostedService):** Периодическая фоновая задача на сервере, проверяющая истекшие заявки и переводящая их из статуса `Approved`/`Active` в статус `Expired`.
4. **Интерфейс тестирования / Клиент:** Swagger UI / Minimal Web Client для генерации HTTP-запросов от имени разных ролей.
5. **Внешний эмулятор СКУД:** Вспомогательный клиентский сценарий, имитирующий считыватель турникета и запрашивающий разрешение на вход по коду заявки.

**Взаимодействия:**
- Клиент $\rightarrow$ API Server: передача JSON по HTTPS (учетные данные, тела заявок, команды согласования).
- API Server $\rightarrow$ База данных: выполнение SQL-запросов через ORM (Entity Framework Core).
- API Server $\rightarrow$ Логирование/Аудит: синхронная запись событий безопасности в транзакции с изменением бизнес-сущностей.

## 7. Откуда продукт получает данные

| Источник | Пример данных | Кто управляет источником | Как продукт использует данные |
| --- | --- | --- | --- |
| **HTTP-запросы: создание заявки (JSON body)** | ID помещения, интервал времени, обоснование допуска, список участников | Заявитель | Проверяет бизнес-правила, создает черновик или новую заявку |
| **HTTP-запросы: согласование ** | Решение (`Approved`/`Rejected`), текстовая причина отказа, ID заявки | Куратор помещения | Валидирует права куратора на конкретный кабинет, изменяет статус заявки, фиксирует решение в аудите |
| **Заголовки авторизации (`Authorization: Bearer <token>`)** | JWT токен | Клиент | Аутентифицирует пользователя, определяет уровень полномочий (RBAC) при вызове каждого эндпоинта |
| **Конфигурационные файлы (`appsettings.json`)** | Строка подключения к БД, секрет подписи токенов, базовые квоты помещений | Разработчик / Администратор среды запуска | Инициализирует параметры запуска сервиса и политики безопасности по умолчанию |
| **Запрос проверки прохода от СКУД ** | ID заявки или электронного пропуска, временная метка попытки входа | Оператор безопасности / Эмулятор турникета | Проверяет право прохода в текущую секунду, возвращает флаг разрешения (`Allow`/`Deny`), логирует проход |

## 8. Минимальное функциональное ядро

**Обязательные функции (MVP к сдаче):**
- Аутентификация пользователей с фиксацией роли (`Applicant`, `RoomManager`, `SecurityOperator`).
- Подача заявки заявителем с валидацией базовых ограничений
- Ролевая маршрутизация: просмотр заявок, закрепленных исключительно за помещением данного куратора.
- Вынесение решения куратором (`Approve`/`Reject`) с фиксацией комментария и запретом самосогласования.
- Проверка статуса допуска оператором безопасности / эмулятором СКУД с возвратом флага разрешения доступа.
- Защита от изменения заявки после вынесения решения

**Функции, которые можно исключить при нехватке времени:**
- Фоновый воркер автоматического перевода статуса в `Expired`
- Отправка email-уведомлений о смене статуса заявки.
- Загрузка вложений
- Сложные составные заявки на группу из нескольких человек (ограничиваемся индивидуальными заявками)

## 9. Стек и путь к первой работающей версии

**Основные технологии:**  
- Язык программирования: C# (.NET 8 / .NET 9)  
- Веб-фреймворк: ASP.NET Core Web API  
- Доступ к данным: Entity Framework Core  
- База данных: SQLite; PostgreSQL - при необходимости масштабирования  
- Документация API: OpenAPI / Swagger

**Технологии, новые для команды:**  
- Тонкая настройка авторизации на основе политик (ASP.NET Core Policy-based & Resource-based Authorization для проверки принадлежности комнаты куратору).

**Внешние сервисы, необходимые для запуска:**  
- Отсутствуют. Продукт полностью автономен и запускается локально.

**Как основные сценарии будут запускаться и проверяться при недоступности внешних сервисов:**  
- Все внешние потребители абстрагированы интерфейсами и заменяются встроенными mock-реализациями или консольными запросами через Swagger/HTTP-файлы.

**Что команда реализует первым, чтобы получить запускаемую версию:**  
- Каркас ASP.NET Core Web API с подключенной базой данных SQLite в памяти/файле, моделью `AccessRequest`, эндпоинтом создания заявки заявителем и эндпоинтом согласования куратором с валидацией смены статуса.

## 10. Локальный запуск

*Заполните после появления запускаемой основы, обязательно к EK1. Если инструкция уже есть в README или другом существующем файле, дайте прямую ссылку вместо дублирования.*

**Требования к окружению:**  
- .NET 8.0 SDK или выше.

**Команды установки и запуска:**  
- `dotnet restore`  
- `dotnet run`  

**Команда или запрос для проверки:**  
- `curl -X GET http://localhost:5000/api/rooms`
