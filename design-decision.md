### D-01. Контекстная авторизация на уровне ресурса

**Контекст:** Угрозы T-01, T-02 и T-05 описывают ситуации, когда аутентифицированный пользователь обращается к чужому ресурсу (заявке) по её идентификатору: пытается согласовать заявку в помещении, за которое не отвечает; согласовать собственную заявку; прочитать детали чужой заявки. Клиентская сторона недоверенная, а ролевая проверка (`Role == "RoomManager"`) сама по себе не отвечает на вопрос, имеет ли конкретный куратор отношение к конкретному помещению и не является ли он автором заявки.

**Решение:** Решение о допустимости операции принимает сервер при каждом запросе к ресурсу, а не клиент. Сервер:

1. Извлекает идентификатор и роль пользователя из доверенного контекста (claims JWT), а не из тела запроса или query-параметров.
2. Загружает целевой ресурс (`AccessRequest`, `RoomPolicy`) по идентификатору из маршрута.
3. Проверяет принадлежность и полномочия по правилу:
   - для согласования: `CurrentUser.Role == RoomManager` **и** `CurrentUser.Id == Room.ManagerId` **и** `CurrentUser.Id != Request.ApplicantId`;
   - для чтения деталей: `CurrentUser.Id == Request.ApplicantId` **или** `CurrentUser.Id == Room.ManagerId` **или** `CurrentUser.Role == SecurityOperator`;
   - для отмены/аннулирования: `CurrentUser.Id == Request.ApplicantId` (отзыв) **или** `CurrentUser.Role == SecurityOperator` (аннулирование).
4. При невыполнении условия возвращает `403 Forbidden` (для чтения — `404 Not Found`, чтобы не раскрывать существование ресурса) и **не изменяет состояние**.

Реализуется через ASP.NET Core Resource-based Authorization (`IAuthorizationHandler` с доступом к загруженному ресурсу), а не только через атрибут `[Authorize(Roles = "...")]`.

**Обоснование:** Ролевая проверка отвечает на вопрос «кто пользователь», но не на вопрос «имеет ли этот пользователь право на этот конкретный объект». Разделение обязанностей (separation of duties) требует, чтобы решение принималось с учётом контекста ресурса и действующего пользователя. Доверенный источник идентичности - claims JWT, проверенные подписью; идентификаторы из тела запроса (например, `applicantId`) для принятия решения не используются. Идентификаторы заявок - UUIDv4 (непредсказуемые), что снижает риск перебора, но не заменяет проверку владения.

**Связанные угрозы:** T-01, T-02, T-05

**Связанные требования:** SR-01, SR-06

**Будущая проверка:**

- **Условие:** В системе есть пользователь `A` (роль `Applicant`), пользователь `B` (роль `RoomManager`, закреплён за помещением `R`), пользователь `C` (роль `RoomManager`, закреплён за помещением `S`). Создана заявка `req-1` в помещение `R` от имени `A`. Создана заявка `req-2` в помещение `R` от имени `B`.
- **Действие:**
  1. `C` отправляет `POST /api/requests/req-1/approve`.
  2. `B` отправляет `POST /api/requests/req-2/approve` (самосогласование).
  3. `A` отправляет `GET /api/requests/req-2`.
  4. `B` отправляет `POST /api/requests/req-1/approve` (штатное согласование).
- **Ожидаемый результат:**
  1. `403 Forbidden`, статус `req-1` не меняется.
  2. `403 Forbidden`, статус `req-2` остаётся `PendingApproval`.
  3. `403 Forbidden` или `404 Not Found`, тело заявки не возвращается.
  4. `200 OK`, статус `req-1` переходит в `Approved`, фиксируются `ReviewedBy` и `ReviewedAt`.

**Ограничения и последствия:** Требуется загрузка ресурса до принятия решения (дополнительный запрос к БД на каждый вызов), что может повлиять на производительность при высокой нагрузке. Возможна оптимизация через кэш или проекции, но не в рамках текущего этапа. Проверка `CurrentUser.Id != Request.ApplicantId` должна выполняться на сервере даже при наличии UI-ограничений, потому что API доступен напрямую.

### D-02. Неизменяемость согласованных параметров и немедленное прекращение допуска

**Контекст:** Угрозы T-03 и T-08 описывают два связанных нарушения жизненного цикла заявки: (1) заявитель после согласования меняет параметры визита (интервал, помещение, состав участников), сохраняя визу согласовавшего; (2) после отзыва или аннулирования заявки точка валидации СКУД по-прежнему возвращает `Allow` в пределах исходного временного окна.

**Решение:** Жизненный цикл заявки управляется сервером через явную машину состояний, а не через свободное редактирование полей.

1. **Неизменяемость после решения.** Эндпоинт `PATCH /api/requests/{id}` доступен только для заявок в статусе `Draft` или `PendingApproval` (до отправки). Сервер проверяет текущий статус перед применением изменений. Для статусов `Approved`, `Rejected`, `Active`, `Cancelled`, `Revoked`, `Expired` изменение параметров визита отклоняется с `409 Conflict`. Разрешены только переходы, предусмотренные машиной состояний:
   - `Approved → Cancelled` (отзыв заявителем);
   - `Approved → Revoked` (аннулирование оператором);
   - `Active → Cancelled` / `Revoked` (досрочное прекращение);
   - `Approved/Active → Expired` (фоновый процессор по истечении времени).
2. **Немедленное прекращение.** При переходе в `Cancelled` или `Revoked` сервер фиксирует новое состояние в БД в той же транзакции, что и запись аудита. Точка `POST /api/access/validate` при каждом вызове загружает **актуальный** статус заявки из БД (не из кэша) и возвращает `Allow` только для статуса `Approved` и только внутри интервала. Для `Cancelled`/`Revoked` — безусловный `Deny` независимо от времени.

**Обоснование:** Согласованные параметры — это санкционированное обязательство; их изменение после решения нарушает целостность согласования (tamper resistance). Явная машина состояний с проверкой допустимых переходов на сервере исключает как случайные, так и намеренные обходы. Немедленное прекращение требует, чтобы решение о проходе принималось по актуальному состоянию, а не по состоянию на момент согласования: отзыв должен действовать с первой секунды после фиксации.

**Связанные угрозы:** T-03, T-08

**Связанные требования:** SR-02, SR-07

**Будущая проверка:**

- **Условие:** Заявка `req-1` в статусе `Approved`, интервал визита покрывает текущее время.
- **Действие:**
  1. Заявитель отправляет `PATCH /api/requests/req-1` с новым `endAt` (позже исходного).
  2. Оператор безопасности отправляет `POST /api/requests/req-1/revoke`.
  3. Эмулятор СКУД отправляет `POST /api/access/validate` с `req-1` через 1 минуту.
  4. Заявитель отправляет `POST /api/requests/req-1/cancel` для другой заявки в статусе `Approved`.
- **Ожидаемый результат:**
  1. `409 Conflict`, исходные параметры `req-1` не изменены.
  2. `200 OK`, статус `req-1` → `Revoked`, запись аудита создана.
  3. `Deny`, `AccessLog` фиксирует отклонённую попытку, статус не меняется на `Active`.
  4. `200 OK`, статус → `Cancelled`; повторная валидация по этой заявке возвращает `Deny`.

**Ограничения и последствия:** Фоновый процессор переводит `Approved/Active → Expired`; между истечением времени и запуском процессора возможен короткий интервал, когда заявка ещё числится `Approved`, но время уже вышло. Это закрывается проверкой времени в `validate` (см. D-03). Отзыв во время активного визита не выводит человека физически, а лишь запрещает повторный вход - это ограничение предметной области, а не решения.

### D-03. Серверная проверка времени и статуса при валидации прохода

**Контекст:** Угроза T-04 описывает подделку временной метки или идентификатора заявки со стороны эмулятора СКУД: запрос `validate` приходит с меткой внутри интервала, тогда как реальное время вне окна, либо с ID заявки, срок которой ещё не наступил. Если сервер доверяет переданной метке, разовый пропуск превращается в «вечный ключ».

**Решение:** Точка `POST /api/access/validate` принимает от СКУД только идентификатор заявки (и, возможно, идентификатор считывателя). Решение `Allow`/`Deny` принимает сервер:

1. Загружает заявку по ID из БД.
2. Проверяет статус: `Allow` возможен только для `Approved`.
3. Проверяет время по **своим** часам: `StartTime <= DateTime.UtcNow <= EndTime`.
4. Проверяет отсутствие признака аннулирования (`Revoked`/`Cancelled`).
5. При успехе переводит статус в `Active` и создаёт запись в `AccessLog` в одной транзакции.
6. При отказе создаёт запись об отклонённой попытке без изменения статуса.

Метка времени из запроса СКУД не используется как основание для решения; она может сохраняться в `AccessLog` как справочная информация, но не влияет на `Allow`/`Deny`.

**Обоснование:** Доверенный источник времени - серверные часы (синхронизированные через NTP на уровне инфраструктуры). Внешняя система не должна определять, наступило ли окно допуска. Проверка статуса и времени в одной транзакции с записью в журнал исключает ситуацию, когда проход разрешён, но событие не зафиксировано, или наоборот.

**Связанные угрозы:** T-04

**Связанные требования:** SR-03

**Будущая проверка:**

- **Условие:** Заявка `req-1` в статусе `Approved`, интервал `[StartTime, EndTime]`. Заявка `req-2` в статусе `Approved`, интервал в будущем. Заявка `req-3` в статусе `PendingApproval`.
- **Действие:**
  1. СКУД отправляет `validate` с `req-1` и меткой времени внутри интервала, но реальное время сервера — вне интервала.
  2. СКУД отправляет `validate` с `req-2` (интервал ещё не наступил).
  3. СКУД отправляет `validate` с `req-3`.
  4. СКУД отправляет `validate` с `req-1` в корректное время.
- **Ожидаемый результат:**
  1. `Deny`, статус не меняется, в `AccessLog` — отклонённая попытка.
  2. `Deny`, статус не меняется.
  3. `Deny`, статус не меняется.
  4. `Allow`, статус → `Active`, запись в `AccessLog`.

**Ограничения и последствия:** Требуется синхронизация часов сервера (NTP). Если сервер работает в нескольких инстансах, все должны использовать одно доверенное время; при расхождении возможны ложные `Deny`/`Allow` на границах интервала. Рекомендуется допуск на несколько секунд, но он должен быть явно задан и обоснован, а не скрыт в коде.

### D-04. Атомарная запись аудита в транзакции с изменением состояния

**Контекст:** Угроза T-06 описывает попытку удалить или исправить запись аудита, чтобы скрыть несанкционированное согласование. SR-04 требует неизменяемости журнала и атомарности фиксации событий: либо состояние и запись аудита сохраняются вместе, либо не сохраняются оба.

**Решение:** Аудит встроен в доменные операции на уровне транзакции БД.

1. **Только добавление.** Прикладной API не предоставляет операций `UPDATE` или `DELETE` для `AuditLogEntry`. Эндпоинты `DELETE /api/audit/{id}` и `PUT /api/audit/{id}` отсутствуют; попытка обращения возвращает `405 Method Not Allowed`.
2. **Атомарность.** Каждая доменная операция (согласование, отклонение, отзыв, аннулирование, валидация прохода) выполняется в одной транзакции БД: изменение статуса заявки и вставка записи в `AuditLogEntry` (или `AccessLog`) происходят вместе. При сбое на любом шаге — `Rollback`.
3. **Атрибуция.** Запись аудита содержит идентификатор действующего пользователя, извлечённый из доверенного контекста (claims JWT), а не переданный клиентом; временную метку формирует сервер.
4. **Защита на уровне БД.** Роль приложения имеет права `INSERT` и `SELECT` на таблицу аудита, но не `UPDATE`/`DELETE`. Это ограничение настраивается в миграциях/скриптах и не зависит от кода приложения.

**Обоснование:** Неизменяемость аудита - это свойство, которое нельзя обеспечить только запретом эндпоинтов: компрометация приложения или SQL-инъекция могут обойти прикладной слой. Поэтому защита строится в два уровня: прикладной (нет операций изменения) и инфраструктурный (права БД). Атомарность гарантирует, что не возникает «полу-состояния», когда статус изменён, а событие не зафиксировано.

**Связанные угрозы:** T-06

**Связанные требования:** SR-04

**Будущая проверка:**

- **Условие:** Заявка `req-1` в статусе `PendingApproval`, куратор `B` аутентифицирован.
- **Действие:**
  1. `B` отправляет `POST /api/requests/req-1/approve`.
  2. `B` отправляет `DELETE /api/audit/{id}` для созданной записи.
  3. `B` отправляет `PUT /api/audit/{id}` с изменённым текстом.
  4. Имитируется сбой БД в момент записи аудита (например, через тестовый флаг или отключение транзакции).
- **Ожидаемый результат:**
  1. `200 OK`, статус → `Approved`, запись аудита создана с `UserId = B`, серверной меткой времени.
  2. `405 Method Not Allowed`, запись аудита не изменена.
  3. `405 Method Not Allowed`, запись аудита не изменена.
  4. Транзакция откатывается, статус `req-1` остаётся `PendingApproval`, запись аудита отсутствует.

**Ограничения и последствия:** Полная неизменяемость на уровне БД требует отдельной настройки прав (не только кода). Если приложение использует одну учётную запись БД с широкими правами, защита ослабляется; это следует зафиксировать как ограничение и адресовать в инфраструктуре. Хранение аудита в той же БД, что и доменные данные, означает, что компрометация БД затрагивает и аудит; вынос в отдельное хранилище - возможное развитие, но вне текущего этапа.

### D-05. Транзакционный контроль лимита вместимости и политики помещения

**Контекст:** Угроза T-07 описывает race condition: два параллельных запроса на согласование проходят проверку лимита одновременно и оба переводятся в `Approved`, превышая вместимость. Угроза T-09 описывает завышение лимита куратором через изменение `RoomPolicy`. Обе угрозы связаны с SR-05.

**Решение:**

1. **Транзакционный контроль при согласовании.** Проверка лимита и изменение статуса заявки выполняются в одной транзакции БД с блокировкой строки политики помещения (`SELECT ... FOR UPDATE` или эквивалент в EF Core через `Serializable`/`RepeatableRead` с явной блокировкой). Алгоритм:
   - загрузить `RoomPolicy` для помещения с блокировкой;
   - подсчитать текущее число `Approved`/`Active` заявок, пересекающихся по времени с целевой;
   - если лимит не превышен - перевести заявку в `Approved`;
   - если превышен - вернуть `409 Conflict` без изменения статуса;
   - зафиксировать транзакцию.
2. **Ограничение изменения политики.** Изменение `RoomPolicy` (лимит вместимости, часы работы) доступно куратору, но:
   - фиксируется в `AuditLogEntry` с указанием, кто и когда изменил;
   - повышение лимита сверх заданного административного порога требует подтверждения администратора (или, как минимум, уведомления);
   - при изменении лимита сервер проверяет, не превышает ли уже согласованное число людей новый лимит (если новый лимит ниже текущей загрузки, изменение отклоняется с `409 Conflict` или требует явного подтверждения с аудитом).

**Обоснование:** Проверка «свободен ли слот» и «создать/согласовать» не могут быть раздельными операциями при конкурентных запросах: между ними состояние может измениться. Транзакционная блокировка строки политики сериализует доступ к критическому ресурсу (вместимость помещения), делая проверку и изменение атомарными. Ограничение изменения политики адресует T-09: куратор легитимно управляет помещением, но не должен единолично обходить нормы безопасности.

**Связанные угрозы:** T-07, T-09

**Связанные требования:** SR-05

**Будущая проверка:**

- **Условие:** Помещение `R` с лимитом 1 человек на интервал `T`. Заявки `req-1` и `req-2` в помещение `R` на интервал `T`, обе в статусе `PendingApproval`.
- **Действие:**
  1. Два параллельных запроса `POST /api/requests/req-1/approve` и `POST /api/requests/req-2/approve` отправляются одновременно.
  2. Куратор `B` отправляет `PATCH /api/rooms/R/policy` с новым лимитом ниже текущей загрузки (например, 0 при одной активной заявке).
  3. Куратор `B` отправляет `PATCH /api/rooms/R/policy` с повышением лимита сверх административного порога.
- **Ожидаемый результат:**
  1. Ровно один запрос получает `200 OK` и переводит заявку в `Approved`; второй получает `409 Conflict`; общее число согласованных заявок на `T` не превышает 1.
  2. `409 Conflict` либо требование подтверждения администратора; изменение фиксируется в аудите.
  3. Требуется подтверждение администратора; попытка без него отклоняется с `403 Forbidden`, событие фиксируется в аудите.

**Ограничения и последствия:** Транзакционные блокировки снижают пропускную способность при высокой конкуренции за одно помещение. Для учебного продукта это приемлемо; при масштабировании возможен переход к оптимистичным блокировкам с версионированием. Выбор конкретного уровня изоляции (`Serializable` vs `RepeatableRead` + явная блокировка) зависит от СУБД и должен быть зафиксирован в реализации; на этапе проектирования важно само требование атомарности. Административный порог — параметр конфигурации, а не жёстко зашитое значение.
